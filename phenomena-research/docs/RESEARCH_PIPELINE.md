# RESEARCH PIPELINE — Phenomena Research Platform

**Status: PROPOSAL v0.1 (2026-08-21). Not implemented.** Companion to `ARCHITECTURE.md` and
`DATABASE_SCHEMA.md`.

---

## 1. The pipeline at a glance

```
QUESTION
   │
   ▼  S1  PLAN            classify intent, pick mode, set budget, choose seeds
   ▼  S2  EXPAND          1 question → 20–150 queries across 13 expansion classes
   ▼  S3  DISCOVER        multi-provider search; every query + every hit recorded
   ▼  S4  TRIAGE          deterministic: dedup, policy gate, relevance prefilter, priority
   ▼  S5  RETRIEVE        fetch cheapest-first; snapshot; hash; store per licence rule
   ▼  S6  EXTRACT         text → claims + entities + attributes + references (cheap model)
   ▼  S7  DEDUPE          content/near-dup/family clustering; independence estimate
   ▼  S8  CHASE           follow references backward → provenance chains → earliest source
   ▼  S9  CORROBORATE     targeted searches for independent confirmation
   ▼  S10 CONTRADICT      targeted searches for explanations; numeric/temporal conflict scan
   ▼  S11 SCORE           10 scores, all components stored
   ▼  S12 ASSESS          information gain; gaps; generate follow-up queries
   │       └── loop to S3 while gain > threshold AND budget remains
   ▼  S13 REPORT          the 15-section dossier
```

Stages S3–S12 form the recursive loop of directive §4. Stages S1, S2, S12 and S13 are the only
ones that use the strong model.

---

## 2. S1 — Plan

Input: the natural-language question plus optional parameters.

The strong model produces a **research plan object** (schema-constrained): domain classification
against `ops.taxonomy_terms`, extracted seed entities (people, places, dates, case names), the
implied time window, the geographic scope, the mode (directive §20), a list of expected
high-value source *types* for this question ("if this is a 1970s US rural sighting, expect: local
newspaper archive, county sheriff records, a regional research group's case file, a later book
retelling"), and the stopping criteria.

The plan is stored on `capture.investigations.parameters` and shown in the report. A researcher
can see the system's strategy before it spends anything.

---

## 3. S2 — Query expansion

Directive §3. One question becomes many queries. **Most expansion is deterministic**, driven by
`ops.taxonomy_terms` and rule templates; the model is used only where language judgement is
genuinely required (period phrasing, translation, plausible witness phrasing).

| # | Class | Generated by | Example (seed: *Dogman sighting, Land Between the Lakes, 1980s*) |
|---|---|---|---|
| 1 | `direct` | rule | `"dogman" "Land Between the Lakes"` |
| 2 | `synonym` | taxonomy table | `upright canine`, `wolfman`, `dog-headed creature`, `manwolf` |
| 3 | `historical` | model + taxonomy `historical_terms` | period-appropriate phrasing for the decade in question |
| 4 | `geographic` | rule (gazetteer expansion) | county, adjoining counties, towns, the lake, the highway, the wildlife refuge, watershed names |
| 5 | `witness` | rule templates | `"saw a creature"`, `"strange animal"`, `"walking on two legs"`, `"eyes reflected"` |
| 6 | `evidence` | rule templates | `+ photograph`, `+ footprint cast`, `+ hair sample`, `+ recording`, `+ track` |
| 7 | `bureaucratic` | rule templates | `incident report`, `unknown animal complaint`, `wildlife officer report`, `sheriff log` |
| 8 | `misspelling` | rule (edit-distance generator, curated) | `dog man`, `dog-man` |
| 9 | `ocr_variant` | rule (OCR confusion matrix: rn→m, l→1, cl→d, ﬂ ligatures, hyphen-linebreaks) | `dogrnan`, `dog- man` |
| 10 | `translation` | model, only when the region is non-English | localized terms + local place names |
| 11 | `entity_combination` | rule, after S6 | `WITNESS+LOCATION`, `WITNESS+DATE`, `WITNESS+INVESTIGATOR`, `LOCATION+DATE`, `CASE+NEWSPAPER`, `DOCUMENT TITLE+pdf`, `ORG+CASE`, `USERNAME+CLAIM` |
| 12 | `exact_quote` | rule, after S6 | a distinctive verbatim sentence in quotes — **the single most effective tool for finding the origin of a retold story** |
| 13 | `debunk` | rule templates | `+ hoax`, `+ debunked`, `+ explanation`, `+ misidentification`, `+ skeptical analysis`, `+ investigation` |

Each generated query is also **routed**: neural-search providers get natural-language phrasings,
keyword providers get operator syntax (`site:`, `filetype:pdf`, quoted phrases, date ranges), and
archive providers get their own query grammar. The router is a lookup table keyed on
`(expansion_class, provider capabilities)`.

Deduplication is applied across the whole set before anything executes (directive §24): queries
are hashed after normalization, and near-identical phrasings are collapsed.

**Budget shaping.** Quick Search executes classes 1, 2, 4, 13 (≈12–20 queries). Deep Dive executes
all 13 across two or three rounds (≈80–150 queries). The class mix is recorded, so a report can
say honestly: "historical-terminology and non-English expansions were not run in this pass."

## 4. S3–S4 — Discover and triage

**Discover** issues queries across all configured providers with per-provider concurrency limits,
writing `capture.search_queries` and one `capture.search_results` row per hit — including hits
that will never be opened.

**Triage** is entirely deterministic and decides which hits become fetches. Every rejection is
written with a reason:

1. **Dedup** — normalized URL already known this investigation, or already in `capture.sources`
   with a fresh snapshot → `deduped`.
2. **Policy** — host denylist, robots disallow, known auth-walled platform → `rejected_policy`.
   (A robots-denied URL is still recorded as a *known source* with `access_status='robots_denied'`.)
3. **Type** — MIME/extension not in the allowlist → `rejected_type`.
4. **Relevance prefilter** — lexical scoring of title+snippet against the expanded term set, plus
   embedding similarity to the question when embeddings are available. Below threshold →
   `rejected_relevance`. No model call.
5. **Priority** — survivors are ordered by a fetch-priority heuristic that deliberately favours
   what mainstream search buries:

```
fetch_priority =
    3.0 × primary_source_type_prior     (gov document, archive, local news, forum, PDF > aggregator)
  + 2.0 × obscurity_prior               (low provider agreement, deep rank, archive-only, old)
  + 2.0 × relevance
  + 1.5 × novelty_prior                 (host/domain not yet in our corpus)
  − 3.0 × known_aggregator_penalty      (content farms and listicle mirrors)
  − 1.0 × depth_penalty
```

The aggregator penalty and the obscurity prior are what make the system behave differently from a
normal search tool: a 2003 GeoCities page and a county historical-society PDF outrank a 2026
listicle that summarizes both.

---

## 5. S5 — Retrieve

**Cheapest path first, always**: plain `undici` fetch + Readability/pdf-parse → provider scrape
(Firecrawl) if that fails or returns boilerplate-only → Playwright only for hosts explicitly
enabled and only when robots permits. Every attempt is recorded in `capture.fetch_attempts`
whatever the outcome.

Snapshot creation: raw bytes hashed (sha256), text extracted, `simhash`/MinHash computed, licence
rule applied to decide `text_storage`, excerpt always retained, embedding computed if a provider
exists. Original bytes go to the object store content-addressed (Phase 4 for media; text-only
before that).

**Archive integration (Phase 3, stubbed in MVP):** for every source, ask the archive provider for
snapshot listings. Three uses: (a) recovering dead links, (b) establishing that a page said
something *different* earlier — a first-class research finding, and (c) dating a page whose own
metadata is absent or wrong (`archive_first_seen` becomes the date provenance).

Watch mode re-fetches with conditional requests and only creates a new snapshot when
`content_hash` changes.

---

## 6. S6 — Extraction

Per snapshot, one cheap-model call (batched where non-interactive), schema-constrained, producing:

- **Claims** — atomized as in directive §8. The prompt's central instruction is *one assertion per
  claim, never a summary of the source*, and every claim must carry the character offsets of the
  span it came from. Offsets are **verified in code**: if `text.slice(start, end)` does not
  contain the quoted span, the claim is rejected and re-requested once. A model cannot invent a
  citation that does not exist in the stored text.
- **Entities** with mention offsets and roles.
- **Claim attributes** — durations, counts, heights, distances, times, bearings, normalized to SI
  with the original phrase retained (`DATABASE_SCHEMA.md` §3.2).
- **References** — every hyperlink, citation, footnote, bibliography line, "as reported by",
  quoted witness, embedded media URL, and named prior source. This is the raw material for S8 and
  is by far the highest-value part of the extraction.
- **Injection flags** — text that attempts to instruct a reader-model. Recorded as data about the
  source (`SECURITY.md` §2), never obeyed.

Long documents are windowed: keyword-anchored regions plus a document-level pass for structure.
Whole books and 300-page PDFs are never sent in one request.

Extraction never decides whether a claim is true, and the prompt contains no vocabulary for it.

---

## 7. S7 — Deduplication and source families

Cascading, cheapest first (`DATABASE_SCHEMA.md` §7): normalized URL → content hash → simhash
Hamming distance ≤ 3 with MinHash banding → embedding cosine ≥ 0.93 → verbatim-shingle overlap
check to confirm.

Confirmed near-duplicates are unioned into a **source family** with a stated basis. A family's
members are one voice. The `INDEPENDENCE_SCORE` for a claim counts distinct families, and the
report always states both numbers:

> *"17 sources report this. They resolve to **3 source families**. 14 of the 17 reproduce wording
> traceable to a single 1978 wire story."*

That sentence is the point of the whole subsystem (directive §10, §16).

Media dedup (Phase 4) uses perceptual hashes with crop/scale/mirror-tolerant matching, and video
uses keyframe-hash sequences; a match between two uploads is a `mirrors` or `derived_from` edge
depending on which is demonstrably earlier.

## 8. S8 — Source chasing and provenance chains

Directive §6. For each extracted reference, in priority order:

1. Resolve it to a URL if possible (hyperlink, DOI, archive lookup, or a targeted search using
   the citation's own words as an `exact_quote` query).
2. Fetch it (back through triage — references get a priority bonus, not a bypass).
3. Write a `source_relations` edge with its `basis`.
4. Recurse until: no further references, a dead end (paywall/offline/dead link), a cycle, the
   depth limit, or the budget limit — and **record which of these ended the chain**.

The chain is then walked backward to produce `interp.provenance_chains`. The earliest source is
the node with no outgoing `derived_from` edge and the earliest defensible date; where dates
conflict, the archive record (`archive_first_seen`) outranks a page's self-reported date.

Reports render chains literally:

```
2026 blog post                    (E — tertiary retelling)      [link]
  └ derived_from ── 2022 YouTube documentary   (D)              [link, transcript]
      └ quotes ──── 2014 forum post            (D)              [archived copy only]
          └ cites ── 1998 newspaper article    (C, contemporaneous?  no — 1 yr later)
              └ quotes ── 1997 eyewitness interview  (B — firsthand)   ← LIKELY PRIMARY
```

A 2026 blog and a 1997 interview are never presented as two sources for the same claim. That
prohibition is enforced by the evidence grader, not by editorial discretion.

## 9. S9–S11 — Corroboration, contradiction, and scoring

### 9.1 Corroboration search (directive §10)
For each high-value claim, targeted queries are generated for: other witnesses at the same
place/time, police/sheriff records, local news of that week, weather and astronomical conditions
for the date, aircraft or launch activity where publicly available, and any sensor/radar record
mentioned. Each result is tested for *independence* against the existing source families before it
is allowed to count.

### 9.2 Contradiction detection (directive §11)
Two mechanisms:
- **Deterministic** — `interp.claim_attributes` interval-overlap scans across claims about the
  same event. Non-overlapping numeric or temporal ranges are contradictions found by SQL, at zero
  token cost, with the exact worked example from the directive ("15 minutes / 3 minutes /
  45 seconds") producing a `temporal` contradiction row.
- **Semantic** — the strong model compares claim sets for identity, attribution, sequence and
  existence conflicts that arithmetic cannot see.

Both are recorded, never resolved. The report shows every version with its source and grade.

### 9.3 Explanation search
Runs the `debunk` expansion class against the case and its distinctive attributes, and grades what
it finds **by the same standard as the claim**. An explanation asserted without evidence is an
F-grade explanation, and is reported as such. An explanation that accounts for some attributes but
not others records its `unaddressed_residual`.

### 9.4 The ten scores (directive §17, §18)

All are 0–100, all store their components, none are multiplied together into a single "truth"
number.

| Score | Subject | Inputs (weights are config, shown in every report) |
|---|---|---|
| `PRIMARY_SOURCE_SCORE` | claim | best evidence grade in its provenance chain; distance in hops to the earliest source; whether the primary is retrievable |
| `PROVENANCE_SCORE` | source/claim | chain completeness; strength of each `basis` (hyperlink/verbatim > llm_inferred); date reliability; archive corroboration of dates |
| `INDEPENDENCE_SCORE` | claim | **count of distinct source families**; witness relationships where known; geographic/temporal separation of reports |
| `CORROBORATION_SCORE` | claim | number and grade of independent corroborating claims; presence of instrumented/record-based corroboration (police report, sensor, weather record) |
| `MEDIA_QUALITY_SCORE` | media | resolution/bitrate; generation distance from the earliest known copy; metadata survival; chain-of-custody documentation |
| `DOCUMENTATION_SCORE` | case | presence of contemporaneous records, official documents, named investigators, physical-evidence documentation |
| `SOURCE_RELIABILITY_SCORE` | source | publisher track record *within this corpus* (how often its claims trace to real primaries), citation behaviour, correction behaviour, transparency of sourcing — **never a hand-assigned trust list** |
| `CONTRADICTION_SCORE` | claim/case | count and severity of contradictions, weighted by the grade of the contradicting sources |
| `OBSCURITY_SCORE` | source | age; count of distinct referring domains in our corpus; provider agreement (found by 1 of 4 providers = obscure); discovery depth; archive-only availability; PDF/scan/OCR origin; local-outlet flag |
| `NOVELTY_SCORE` | source/claim | 1 − max cosine similarity to existing corpus; count of entities and claims not already in the DB; whether it introduces a new source family |

**Evidence grade (A–F)** is *not* a score — it is a deterministic classification from directive §9,
computed by rule from `evidence_type` + provenance position + retrievability. Grades never move
because of how interesting a claim is.

**The discovery ranking** the directive asks for in §18 is a report ordering, not a hidden score:
items are surfaced by `evidence_value × obscurity × novelty`, with all three shown, so a
researcher can see exactly why something is at the top.

## 10. S12 — Assess, and the autonomous loop (directive §30)

After each round the assessor computes **information gain**:

```
gain(round) = w1 × new_source_families
            + w2 × new_claims_grade_A_to_C
            + w3 × new_entities
            + w4 × chain_depth_increase          (did we get closer to a primary source?)
            + w5 × new_contradictions_or_explanations
```

It then produces (strong model, schema-constrained): the current gap list, the ranked next
queries, and a recommendation to continue or stop.

**Stopping conditions — all enforced in code, not by the model:**

| Condition | Default (Deep Dive) |
|---|---|
| Cost cap | configured USD ceiling per investigation |
| Search cap | max total queries |
| Page cap | max fetches |
| Wall-clock cap | max minutes |
| Depth cap | max recursion depth for chasing |
| Diminishing returns | `gain(round) < threshold` for 2 consecutive rounds |
| Family saturation | no new source family in 2 rounds |

Whichever fires first wins, and the report names it. A run that stops on budget is labelled
**TRUNCATED** and ships with its unexecuted query queue attached, so it can be resumed later
rather than repeated.

## 11. Research modes (directive §20)

Each mode is the same pipeline with a different plan template, expansion mix, priority weighting
and report shape.

| Mode | What changes |
|---|---|
| **Quick search** | 1 round, ~15 queries, no chasing beyond depth 1, no corroboration pass. Interactive; not batched. |
| **Deep dive** | Full loop, all expansion classes, chasing to depth 4–6, both corroboration and explanation passes. |
| **Case file** | Deep dive scoped to one incident; report is a dossier with a full timeline, witness table, all media, and every contradiction enumerated. |
| **Person** | Entity-centric: trace one witness/investigator/official across cases; strict PII rules (`SECURITY.md` §8) — professional/public activity only. |
| **Location** | Geographic: bounding-box and place-name expansion, gazetteer-driven; produces the cluster analysis of §12. |
| **Media** | Provenance-first: perceptual-hash search for earlier copies, archive sweeps of hosting pages, earliest-upload determination, transformation analysis. |
| **Document hunt** | Repository-first: `filetype:` queries, government repositories, FOIA-log searches, university and library catalogues, archive CDX for removed documents. |
| **Timeline** | Chronology assembly across all claims about a case or region, with precision bands rendered honestly. |
| **Connection hunt** | Graph-first: shared entities, shared source families, geographic and temporal proximity between apparently unrelated cases; every proposed connection carries its supporting claim ids. |
| **Watch** | Scheduled re-run of a saved query set; diffs against `last_result_hash`; reports only what is new. |

## 12. Geospatial and temporal analysis (directive §13, §14)

**Geospatial** (Phase 5): locations resolved with an explicit `precision_class`; clustering with
DBSCAN over points weighted by precision (a county-level point never contributes to a
tight cluster). Proximity to roads, rivers, forest boundaries, water bodies, airports, and
military installations is computed from open datasets where licensing permits.

Every spatial output carries a fixed caveat, and the system will not emit a cluster claim without
it: **correlation with a feature is not evidence of a causal relationship, and reporting density
tracks population, road access, and local media coverage before it tracks anything else.**

**Temporal**: timelines built from `event_date` ranges with precision bands drawn as bands, not
points. Wave detection compares report density against a baseline that accounts for media-coverage
bursts — a spike in *reports* immediately after a famous news story is flagged as a possible
publicity artifact rather than a phenomenon. Cases predating their famous retellings are surfaced
explicitly; that pattern is one of the most valuable findings the system can produce.

## 13. Media forensics (directive §12, Phase 4)

Preserve the highest-quality publicly obtainable version. Extract what is present: resolution,
codec, frame rate, bitrate, container metadata, EXIF (usually absent — platforms strip it), file
hash, perceptual hash, keyframes, thumbnails.

Detect **signals** of recompression, cropping, mirroring, colour modification, and resampling, and
express them as evidence of a *derivative relationship* between copies, ordering them into a
generation tree. Search for earlier copies by perceptual hash within the corpus and via provider
image search where terms permit. Establish the earliest known public upload with its evidence
(archive capture, page date, platform-declared upload date) and its uncertainty.

Two hard rules: absence of manipulation signals is **never** reported as authenticity, and no
media is ever labelled "fake" by the system — only "this copy is demonstrably derived from that
earlier copy," which is a fact about files.

## 14. S13 — The report (directive §21)

Every investigation produces the same fifteen sections, in this order:

1. **Executive summary** — what the evidence establishes, what it does not, in the epistemic
   register required below.
2. **Most important discoveries** — ranked by evidence value × obscurity × novelty, each showing all three.
3. **New / obscure sources** — with `OBSCURITY_SCORE` components visible.
4. **Primary sources** — grade A and B only, with retrieval status.
5. **Claims** — grouped by subject, each with grade, provenance position, and a one-click span link.
6. **Corroboration** — sources *and* families, always both numbers.
7. **Contradictions** — every version of every conflicting attribute, with sources.
8. **Conventional explanations** — graded, with unaddressed residuals stated.
9. **Media evidence** — provenance trees and earliest-known copies.
10. **Source provenance** — the rendered chains.
11. **Timeline** — precision bands, not false points.
12. **Geographic information** — with the correlation caveat.
13. **People / organizations** — public professional roles only.
14. **Unanswered questions and next searches** — the live queue.
15. **Confidence assessment and audit** — what ran, what was skipped, what was unavailable, what
    the budget cut off, which providers were configured, model and prompt versions.

**Required epistemic register.** Report prose is constrained by prompt and reviewed by rule. The
system writes:

> *"The evidence establishes X. Y remains unexplained. Hypothesis Z is consistent with the
> available evidence but is not established by it."*

It does not write "this proves", "this confirms", "debunked", "hoax", or "hallucination" unless
quoting a source — and when it does, that string is rendered as an attributed quotation. A
lint pass over the generated report rejects assertive-truth vocabulary outside quotation marks and
regenerates the section.

Formats: Markdown (canonical, diffable), JSON (the same content, machine-readable), HTML for the
dashboard. Reports are stored with the investigation and are reproducible from the ledger.

## 15. What the pipeline will not do

- It will not rank an interesting claim above a boring one on the strength of interest.
- It will not fill a gap with inference. An unknown is reported as unknown.
- It will not present a claim without at least one retrievable source or an explicit
  `access_status` explaining why the source could not be retrieved.
- It will not let extraction output become an action: a URL discovered inside scraped text goes
  back through triage, validation, robots, and budget like any other candidate.
- It will not treat its own prior output as evidence. Interpretation rows are never inputs to
  evidence grading.
